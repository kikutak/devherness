# ADR-0001: オーケストレーション基盤をGitLab CI/CDのみに限定する

## Status

Accepted (2026-08-13)

## Context

マルチエージェント自動開発ループ(設計→コーディング→レビュー→修正→マージ→検証→再設計)を駆動するには、非同期に発生するイベント(MRへのpush、レビュー結果、検証結果)を受けて次のフェーズを起動する仕組みが必要である。一般的にはWebhookリスナーやジョブキューを持つ常駐オーケストレータサーバを構築するのが定石だが、本プロジェクトでは「常駐のWebhookリスナーやジョブキューを持つ専用サーバ/VM/K8sは新規に用意しない」という制約があり、**GitLab CI/CDのネイティブ機能のみでループの状態遷移とトリガーを実現する**ことが求められている。

GitLab CI/CDには以下の制約がある。
- パイプラインは push、`merge_request_event`、schedule、API/Web trigger等のイベントでのみ起動し、**MR/Issueのラベル変更単独では新規パイプラインは起動しない**。
- 常駐プロセスを持たないため、外部からの非同期通知(例:検証環境の完了通知)を即座に受け取る仕組みがない。

## Decision

以下の二段構成でオーケストレーションを実現する。

1. **イベントチェーン方式(主軸)**: 各jobが処理の最後に、次に進むべきフェーズを`LOOP_PHASE`等の変数付きでPipeline Trigger APIを呼び出して明示的に起動する。あわせて、コーディング役のMRブランチへのpush、検証役の専用トラッキングブランチへのpushなど、GitLabが標準でパイプラインを起動するイベント(push, `merge_request_event`)も可能な限り活用し、明示的なTrigger API呼び出しを最小限にとどめる。
2. **スケジュールリコンサイラ(補完)**: Pipeline Schedule(GitLab組み込みのcron機能)で数分間隔のポーリングジョブを走らせ、(a)初回Issueキックオフの取りこぼし救済、(b)Trigger API呼び出し失敗などで停止した状態の検知・再送、(c)loopガードの再確認、(d)タイムアウト検知を行う。happy pathの主エンジンとはせず、あくまでセーフティネットと位置付ける。

詳細なトリガーの組み合わせと状態遷移は [設計ドキュメント 5章](../design/multi-agent-dev-loop.md#5-状態管理トリガーの具体的仕組み) を参照。

## Consequences

**メリット**
- 専用インフラの新規構築・運用コストがゼロ。GitLabプロジェクトの設定のみで完結する。
- すべての状態遷移がGitLabの標準UI(パイプライン一覧、MR/Issueのラベル・コメント)で追跡可能。

**デメリット・トレードオフ**
- ラベル変更単独ではパイプラインが起動しないGitLabの制約により、「各jobが次のjobを明示的に呼ぶ」規律を全ロールのスクリプトに徹底する必要があり、設計・実装が複雑化する。
- スケジュールリコンサイラの起動間隔(cronの精度)が、Trigger API呼び出し失敗時などの唯一の遅延要因として残る。
- 複数MR/Issueが並行して自律ループを回す際のRunner capacityやレースコンディション対策([設計ドキュメント 5.2節](../design/multi-agent-dev-loop.md#52-トリガーの具体的な組み合わせ)の`resource_group`)を別途設計する必要がある。
