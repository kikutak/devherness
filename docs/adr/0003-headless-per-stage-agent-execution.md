# ADR-0003: エージェント実行モデルをステージごとの独立headless実行にする

## Status

Accepted (2026-08-13)

## Context

設計・コーディング・レビュー・テスト・検証という異なる役割を持つエージェントをどう実行するかには、大きく二つの選択肢がある。

1. **単一の長寿命Claude Codeセッション内で、`.claude/agents`のサブエージェント機能を使ってロール間のタスク委譲を行う。**
2. **GitLab CIのステージ(job)ごとに、独立した`claude -p`(headless, `--output-format json`)プロセスを起動し、ロールをまたぐ文脈はgitオブジェクト(コミット、設計doc、レビューコメント、stateファイル)経由で明示的に受け渡す。**

サブエージェント機能は、同一セッション内でオーケストレータ役のエージェントが複数の子タスクに委譲する用途に向いている。一方、本ループでは以下の要件がある。

- ロールごとに別のGitLab Access Tokenを発行し最小権限を徹底したい(セキュリティ・権限設計)。
- どのロールがいつ何をしたかをCIジョブ単位でログ・監査したい。
- 各ロールをGitLab CIのステージ・並列度・リトライポリシーとして独立に制御したい。
- コーディング役とレビュー役は別コンテナ・別Runner Tag(例:検証役は検証環境専用ネットワークに限定)で実行したい場面がある。

## Decision

各ロール(設計・コーディング・テスト・レビュー・検証)を、GitLab CIの**別々のjob(別コンテナ・別プロセス)**として実行し、それぞれ独立した`claude -p` headless呼び出しで実現する。ロール間のコンテキストはセッション内の会話履歴ではなく、gitコミット・設計doc・MRコメント・[ADR-0002](0002-state-management-labels-and-repo-file.md)で定めたstateファイルを介して明示的に受け渡す。

`.claude/agents`のサブエージェント機能は、ロールをまたいだ権限分離が要件である本設計では主役にしない。ただし、各ロールのjob内部でさらに細かい内部分業をしたい場合(例:コーディング役が「実装」と「セルフレビュー」を分ける)は、job内でサブエージェント定義を併用してよい。

詳細は [設計ドキュメント 2.2節](../design/multi-agent-dev-loop.md#22-ロールとclaude-code実行モデルの対応付け) を参照。

## Consequences

**メリット**
- ロールごとのトークン分離・最小権限([設計ドキュメント 9章](../design/multi-agent-dev-loop.md#9-セキュリティ権限設計))が自然に実現できる。
- CI jobログがそのままロールごとの監査ログになり、GitLabのパイプラインUIで各フェーズの実行結果を独立して追跡できる。
- コンテナイメージ・Runner Tag・タイムアウト・リトライポリシーをロールごとに最適化できる(例:検証役のみ検証環境専用ネットワークに限定)。

**デメリット・トレードオフ**
- セッションをまたぐため会話的な文脈(セッション内の暗黙の合意事項等)は失われる。「引き継ぎ情報は必ずファイル/コメントとして明示的に残す」という規律を全ロールのプロンプト設計で徹底する必要がある。
- ロール間の情報伝達がgit操作・API呼び出しを介するため、単一セッションでの委譲に比べてレイテンシがわずかに増える。
- headless出力(JSON)のパース失敗時のリトライポリシーを別途設計する必要がある([設計ドキュメント 11章](../design/multi-agent-dev-loop.md#11-未解決将来検討事項)の未解決事項)。
